# Batch D — 출시 전 안정성·시각 완성도 정리

## 0. 범위와 현재 판정

먼저 이 문서 전체를 읽고 실제 현재 소스를 확인한다. 실행에 필요한 C 검수 판정은 이 문서에 포함돼 있다. `BATCH_C_REVIEW.md`가 함께 있으면 상세 근거로 참고하되, 없다는 이유만으로 작업을 중단하지 않는다.

이번 범위는 다음과 같다.

- **D-A01:** 실제 배포/로딩 에셋과 검증 목록의 불일치 해소. shipping 에셋 검사 실패를 닫는다.
- **C-P01:** 박수의 몸동작과 반응 문구의 주체를 더 명확하게 한다.
- 기존 **F16/F17/F18/F19/F20/F21/F22/F23**.
- **F24는 대상 선별 문서만 작성**한다. 전역 이미지 재가공/밀도 변경은 하지 않는다. F25 신규 음식 선택은 구현하지 않는다.

C의 사진 결과·수첩 사진·단체사진·접수 피드백 및 B-E01/B-V01 개선은 증빙 범위에서 승인됐다. F11의 두 선택/전환도 유지한다. C-P01은 버그 재구현이 아니라 참여감을 높이는 작은 시각 보완이다. 에셋 검사는 별도 **출시 전 필수 해결 항목**이다.

참고 baseline:
- 첫 화면 전체 응답 **3,509,311 bytes**, 게임 에셋 **3,094,744 bytes**.
- 마지막 최종 기록: dev 88 PASS / 3 production-only SKIP, production 14 PASS. 서로 다른 논리 테스트 91개. 다음 실행의 테스트 수는 새 테스트에 맞춰 바뀌어도 되지만 상세와 요약은 일치해야 한다.
- 기존 에셋 검사: 35개 등록 항목, `Unlisted shipping asset` 40건으로 실패. 23개는 단계 로더의 최적화 WebP와 연결되고 17개는 해당 파일에서 직접 사용을 확인하지 못했다. 이를 그대로 미사용/무해하다고 간주하지 않는다.

### 작업 방식

D를 내부 소단위로 나눠 구현·검증하되, 매 소단위마다 사용자에게 파일을 전달하거나 승인을 기다리지 않는다. 필요한 정보가 저장소에서 해결되지 않는 진짜 blocker일 때만 멈춘다. 마지막에 통합 검수용 ZIP 하나를 만든다.

## 1. 보호할 기준

- 작업 직전 commit, dirty 상태, 소스/테스트/에셋 해시를 기록한다. 기존 미커밋 변경은 보존한다. reset/clean/stash 또는 기존 작업 덮어쓰기를 하지 않는다.
- 다른 작업/에이전트가 같은 파일을 바꾸는 것을 발견하면 덮어쓰지 말고 충돌 범위를 보고한다.
- 기존 배경·미니미 얼굴/헤어/옷·실사 사진·커플 이름·예식/교통 정보·하객측별 조건·식사 순서를 임의로 바꾸지 않는다.
- A/A1의 짧은 안내, 정보형 수첩, 명시적 닫기, 두 버튼 식장 알림, 이름 오류/포커스, 모바일 글자/터치 크기를 유지한다.
- B의 바닥 판정/발 앵커/정상 접근점, 경로 안내, 언제든 청첩장, 메시지 생략, 단계별 로딩, 키보드 완주를 유지한다.
- C의 두 사진 결과, 실제 외형, 명시적 복귀, 단체사진의 플레이어 위치, 일회 진행도/접수 알림을 유지한다.
- 의미 없는 점수·HP·재화·시간 압박·필수 미니게임, 새로운 서버/오디오 시스템, 외부 공유/전송을 추가하지 않는다. QA는 로컬 테스트 데이터와 전송 stub만 사용한다.
- 크림/골드/딥그린과 현재 픽셀 프레임을 기반으로 다듬는다. 둥근 SaaS 카드, 과도한 그림자/글래스 효과, 전면 재디자인은 하지 않는다.
- 실제 폰/사용자가 아닌 자동 브라우저 검증은 그렇게 표기한다. 파일/함수명은 탐색 힌트이지 현재 존재를 보증하는 목록이 아니다.

## 2. D-A01 — 에셋 검사를 실제 제품과 일치시키기

**가장 먼저 수행할 P1 작업.** `verify:assets`를 실패한 채 '전체 통과'로 보고하지 않는다.

### 2.1 먼저 인벤토리를 대조한다

실제 `assetManifest.ts`, `verify-assets.mjs`, `stageAssets.ts`, 갤러리 데이터, CSS/폰트 참조, 동적 URL 생성, 에셋 생성/최적화/복사 스크립트, production 출력물을 확인한다.

현재 제공된 검사기는 `/assets/lacitta`와 제한된 확장자/그룹을 중심으로 동작하지만 단계 로더는 `/assets/optimized`도 쓴다. **40개 기존 PNG를 manifest에 추가하는 것만으로 끝내지 않는다.** 실제 배포 파일과 실제 로딩 URL을 모두 포함하는 대조가 필요하다.

다음 표를 `asset-audit.md` 또는 JSON으로 만든다.

`원본 → 런타임 키 → 실제 URL → 사용 장면/로딩 단계 → production 포함 여부 → 검사 계약 → 출처 기록 → 처리 결과`

- 정상 사용: 실제 최적화 파일의 존재/디코딩/크기/투명도/시트 구조까지 검사한다.
- 제작용 원본·이전 버전: 직접/간접 참조와 빌드 복사를 확인한 뒤 분류한다. public에서 제외해야 한다면 원본은 삭제하지 않고 명시적인 제작용 위치에 보존하며 생산 도구/참조도 함께 수정한다.
- 알 수 없음: 무해한 것으로 화이트리스트 처리하지 않는다. 조사 결과와 미해결 사유를 남긴다.
- 출처/사용 근거는 저장소와 사용자가 제공한 실제 기록으로만 채운다. 출처·라이선스·승인을 통과용 문구로 만들어 쓰지 않는다. 근거가 없으면 필요한 항목을 구체적으로 표시한다.

### 2.2 검사와 로더 사이의 관계를 고친다

가능하면 공통 메타데이터를 사용하거나 자동 대조가 되는 관계를 만든다. 같은 데이터를 두 군데에서 수동 관리해 다시 어긋나게 하지 않는다. 다만 게임 로더/엔진 전체를 재작성할 필요는 없다.

- 실제 PNG/WebP/JPEG/폰트 등 사용 포맷, 경로, 파생본을 검사 대상에 포함한다.
- 실제 스프라이트/합성 아틀라스 계약과 레거시 32×48 시트 계약을 구분한다. 모든 파일을 레거시 크기에 맞추려고 축소하지 않는다.
- `initial/share`만 있는 예전 모델을 현재 단계별 로딩과 정합적으로 맞춘다. 새 등록이 Boot의 전량 preload를 되살리면 안 된다.
- 출처·중복 키·없는 경로·잘못된 크기/시트·투명도·예산 검사를 유지한다. 확장자/폴더를 스캔에서 제외해 오류를 숨기지 않는다.
- 예전 파일당/초기 예산이 현재 승인된 제품 계약과 다르면 이유와 새 예산의 범위를 문서화한다. 모든 제한을 무한대로 풀거나 개별 파일 크기에 무조건 맞추지 않는다.
- 실제 production 첫 화면 **전체 5,000,000 bytes 이하**를 유지하고 C 대비 증감 근거를 별도로 측정한다. manifest 내부 부분합을 실제 네트워크 전체값 대신 쓰지 않는다.

### 2.3 완료 조건

1. 정상 shipping `npm run verify:assets`가 범위 축소 없이 exit 0.
2. 실제 production 출력의 사용 에셋과 등록 정보가 맞으며 알려지지 않은 shipping 파일이 없다. 비배포 원본은 보존 위치/생성 경로가 명시돼 있다.
3. 최적화 URL 하나를 누락하거나 참조를 깨뜨린 음성 테스트에서는 검사가 실패한다. 중복 키, 누락 파일, 깨진 이미지/잘못된 시트 계약 등의 대표 fixture도 실패해야 한다.
4. 양쪽 여정과 후반 사진/뷔페/청첩장에 missing texture가 없고 초기 전송량/지연 로딩이 회귀하지 않는다.
5. 40개 각각의 처리가 추적 가능하다. 전체가 미사용이라는 가정으로 일괄 삭제하지 않는다.

출처 등 저장소에 없는 근거 때문에 정상 shipping 통과를 만들 수 없다면 **BLOCKED**로 적고 어떤 자료가 필요한지 특정한다. 검사 완화로 PASS를 만들지 않는다.

## 3. F16 — 버튼 상태 통일

공통 idle / hover / focus-visible / pressed / disabled 의미를 DOM과 canvas에 맞춘다.

- press → 바깥으로 드래그 → release/cancel 시 실행하지 않고 실제 포인터/포커스 상태에 맞는 스타일로 복원한다.
- 터치 pointercancel, 포커스 이동, 청첩장 왕복, 장면 종료/복귀에서도 눌린 금색/틴트가 남지 않는다.
- 사용 불가 버튼은 보이는 disabled 또는 숨김 중 상태에 맞게 처리하고, 포인터/키보드 동작도 일치시킨다.
- 한 입력은 한 번만 실행한다. 길게 누른 Enter/Space가 새로 열린 모달의 버튼을 연속 실행하지 않는다.
- focus indicator를 삭제해 시각 문제를 가리지 않는다. 필요 없는 다중 테두리는 줄일 수 있지만 키보드 focus는 명확하게 유지한다.
- 기존 오류 메시지, 접근성 이름, 최소 44×44 CSS px 핵심 타깃을 보존한다.

완료 조건: 취소/정상 실행/disabled/키보드의 실제 입력 증빙과 시각 상태가 일치하고, 장면 전환에 stale handler가 남지 않는다.

## 4. F17 — 모션 감소 설정을 모든 관련 장면에 일관되게

현재 새 C 연출은 보존하면서 포토부스/신부대기실/단체사진의 플래시, REC 반복 점멸, 장식 반복 애니메이션을 점검한다.

- 공통 효과 선호 상태를 사용한다. `prefers-reduced-motion: reduce`에서는 프로젝트 기준으로 전체 화면 흰 플래시/반복 REC 점멸을 사용하지 않는다.
- 정적인 셔터/촬영 완료 표시로 성공을 알리고 동일한 진행도·결과를 제공한다.
- 박수/환호는 정적인 서로 다른 표현으로도 구별돼야 한다.
- 필수 조작이나 성공 피드백을 삭제하는 것이 아니다. 이동을 멈춰 게임을 진행할 수 없게 만들지 않는다.
- 실행 중 설정 변경과 장면 재방문을 확인하고, 리스너가 계속 늘어나지 않게 한다.
- 정상 모드의 기존 절제된 효과는 보존한다. 이 설정 검증을 모든 광과민/접근성 안전성의 인증으로 표현하지 않는다.

완료 조건: 세 사진 장면 모두 정상/감소 모드로 완료, 감소 모드에서 전체 플래시와 반복 REC 없음, 사진/진행도/명시적 복귀 동일.

## 5. F18 — 새로고침 후 이어하기

### 저장 정책

프로젝트 내 별도 namespace의 작고 versioned checkpoint를 사용한다. 기존 방명록 데이터와 키/수명을 분리한다.

기록할 의미 상태: 이름, 외형, 하객측, 이동 방식/유효 경로, 완료 활동, 식사 여부/순서, 예식/사진 완료 여부, 재개 가능한 안전한 지점.

- 안정된 장면/활동 경계에 저장한다. 매 프레임 좌표, DOM, 실행 중 tween, 타이머 callback을 직렬화하지 않는다.
- Intro에 유효한 기록이 있을 때 `이어하기 / 처음부터`를 제공한다. 저장이 없는 첫 방문은 현재 흐름을 유지한다.
- 현재 정당한 상태 모델로 복구한다. 촬영/접수/식사를 중복 인정하거나 재실행하지 않는다. 복구 때문에 필수 조건이 새로 생기거나 이미 완료한 활동을 다시 시키지 않는다.
- 청첩장 중 진척 유지, 빠른 재시작, 새로고침, 백그라운드 복귀와의 관계를 점검한다.

### C 사진 결과와 함께 설계한다

C의 원본 사진은 현재 세션 한정이다. 체크리스트만 복구하고 사진이 아무 설명 없이 사라지면 경험이 어긋난다.

권장: 촬영 완료 시점의 작은 **재구성 메타데이터**(활동/외형/구도 버전 등)를 저장하고, 동일한 현재 자산으로 필요한 결과를 지연 재구성한다. 사진을 다시 찍었다고 진행도를 증가시키지 않는다. 이미 완료된 사진에 나중 외형을 잘못 대입하지 않는다.

- 고해상도 사진 base64를 localStorage에 넣지 않는다.
- 원본 사진 파일을 저장하지 않는다는 점과 버전 호환 범위를 기록한다.
- 재구성이 불가능한 구버전 기록은 명확한 안전한 대체 상태로 처리한다. 사진을 복원했다고 거짓 표시하지 않는다.

### 실패 내성

저장소 접근 거부/용량 초과, 잘못된 JSON, 모르는 schema/에셋 버전, 범위 밖 외형 값, 모순된 진행도를 검사한다. 실패 시 현재 게임은 계속 이용할 수 있어야 한다. 자동으로 방명록 전체나 다른 앱 데이터를 삭제하지 않는다.

`처음부터`는 진행 checkpoint와 현재 세션 사진을 정리하되 이미 저장된 방명록은 임의 삭제하지 않는다.

### 완료 조건

- 로비 필수 활동 일부 완료 후 reload → Continue에서 외형/측/경로/진행이 유지됨.
- 두 사진 중 1장/2장 이후 각각 reload → 진행도·사진 의미가 일치함.
- 식사 먼저/나중 경로의 reload 후 중복 식사 없음.
- 사진 촬영 중/예식 반응 중 reload는 안전한 경계로 복원하고 callback 중복 없음.
- 완료/메시지 생략/재시작도 올바르게 작동함.
- 저장 불가·손상·구버전에서 화면이 막히지 않음.
- 처음부터를 고른 뒤 다시 reload해도 이전 방문을 유령처럼 이어가지 않음.

## 6. F19 — 주차장을 의도적인 안내도로 정리

선택할 기본 방향은 **작은 주차 안내 지도**다. 다른 고품질 배경을 교체하지 않고 현재 평면 주차 장면의 의도를 분명하게 만든다.

- 주차 칸/정차 차량/플레이어 차량을 같은 top-down 시점과 픽셀 밀도로 맞춘다. 상세 후면 자동차 sprite를 평면 주차칸 위에 그대로 두지 않는다.
- `주차 안내도`처럼 지도라는 문맥을 짧게 준다. 기존의 현재 목적지 표기/B3/타워/잘못된 경로 구분을 유지한다.
- 흑백 또는 낮은 채도 바탕+경로 색을 강조하되 주차 구획/방향은 읽히게 한다. 지나친 꽃/장식으로 정보를 가리지 않는다.
- 실제 경로·주차지원·출구 정보를 새로 지어내거나 변경하지 않는다. 정확한 실측 평면도인 것처럼 보이게 만들지 않는다.
- 원본 이미지는 보존한다. 새 아이콘이 필요하면 작은 일관된 게임용 asset으로 관리하고 D-A01 검사에 포함한다.

완료 조건: 움직이는 차와 정차한 차가 같은 시점, B3/타워/오답의 텍스트·경로가 명확, 320에서도 이해 가능, 경로 복귀·진행 유지.

## 7. F20 — 뷔페 실사 사진을 의도적인 사진 카드로

실사 음식은 보존한다. 갑작스러운 대형 사진 콜라주 대신 기존 액자/수첩의 재료와 맞는 `뷔페 미리보기` 구성을 사용한다.

- 모바일 한 화면 3~4장 정도 또는 명시적인 이전/다음이 있는 사진 카드로 구성한다. 억지로 한 화면에 6장을 크게 채우지 않는다.
- 같은 프레임·간격·일관된 이미지 비율을 사용하되 음식이 잘려 무엇인지 모르게 되지 않는다.
- 식사 장면/미니미의 맥락이 일부 남도록 한다. 모든 사진을 넘겨야 식사를 마칠 수 있게 만들지 않는다.
- `식사를 마친다`는 직접 접근 가능하게 유지하고 식사 먼저/중복 식사 방지·운전자 대사를 보존한다.
- 자동 재생/강제 스와이프/새 메뉴 선택 게임을 추가하지 않는다. 버튼과 키보드로도 탐색 가능해야 한다.
- 이름/메뉴/제공 사실은 실제 콘텐츠에 있는 것만 사용한다. 실사에 pixel filter를 씌우지 않는다.
- 현재 필요한 렌더링 크기와 지연 로딩을 고려하되 원본을 훼손하지 않는다.

완료 조건: 의도적인 사진 자료로 읽히고 종료 조작이 사진에 가려지지 않음. 320/393/430, 양쪽 식사 순서·키보드 흐름 통과.

## 8. F21 — 로비 장소 라벨의 시각 언어 정리

검은 직사각형 태그를 조금 더 게임 안의 안내판처럼 다듬는다. **가독성을 낮추거나 장소를 숨겨야 탐색이 된다고 판단하지 않는다.**

- 얇은 픽셀 테두리/명패/필요한 소형 아이콘 등 현재 재료를 이용한다. 모든 라벨에 여러 겹 프레임을 추가하지 않는다.
- 필수 목적지와 편의시설의 위계를 만들되 라벨 문구/위치와 실제 상호작용 영역은 일치해야 한다.
- 14 CSS px 이상 핵심 라벨과 44px 핵심 터치 영역을 유지한다. 긴 라벨 때문에 서로/수첩/청첩장 버튼을 덮지 않게 한다.
- 수첩과 연결된 위치 강조는 짧고 절제되게 하고 감소 모드에서 정적 대안으로 제공한다.
- 키보드 목적지 목록과 동일한 이름·접근점·진행도를 쓴다. 현재의 정보형 수첩을 메뉴 순간이동 시스템으로 바꾸지 않는다.
- 물리적 충돌 영역은 라벨의 새 모양과 별개다. 배경 벽/가구/발 앵커를 건드리지 않는다.

완료 조건: 320/393/430 및 desktop에서 장소 식별/타깃/겹침 검증, 장면 그림의 중요 요소를 덜 가림, 필수 장소 전부 접근 가능.

## 9. F22 — 게임 바깥 여백을 하나의 프레임으로

- 현재 720×1280 논리 장면의 비율/구도는 유지한다. 화면을 채우려고 배경을 찌그러뜨리거나 중요한 영역을 잘라내지 않는다.
- 크림 상단·연녹색 하단·바깥 배경의 경계를 같은 웨딩 편지지 느낌으로 정리한다. 선택한 UI 색과 대비는 유지한다.
- 별/하트는 장식으로만 사용하고 화면을 산만하게 채우지 않는다.
- letterbox가 있는 화면에서는 작은 보조 크롬을 활용할 수 있지만, **여백이 없는 320×568에도 모든 필수 조작이 존재**해야 한다.
- 청첩장/수첩을 이동시키더라도 44px 타깃, 가독성, 키보드, 장면 안전 영역을 보존한다. 중복 HUD나 큰 상시 막대를 추가하지 않는다.
- 실제 viewport screenshot을 기준으로 확인한다. full-page PNG의 숨은 overflow를 실제 화면 여백으로 오해하지 않는다.
- 화면 회전·주소창 높이 변화·safe area·이름/메시지 입력 키보드와 기존 가로화면 대안을 점검한다. 실기기에서 확인하지 못한 동작은 미검증으로 남긴다.

완료 조건: 짧은/긴 세로·desktop·landscape에서 의도적인 바깥 프레임, 불필요한 body 스크롤/잘림/필수 조작 손실 없음.

## 10. F23 + C-P01 — 걷기와 축하 동작

### F23 걷기

- 가능하면 현재 합성 미니미에 맞는 2~4프레임 걷기를 추가한다. 얼굴/안경/헤어/옷과 피벗/발 기준이 전 프레임에 맞아야 한다.
- cadence는 실제 이동 거리와 연결하고 도착 때 idle로 안정적으로 돌아온다. 제자리에서 발만 움직이거나 느린 FPS에서 걸음/속도가 달라지지 않게 한다.
- 기존 pathfinding/feet clearance, 즉시 입력 응답, 다른 목적지 탭으로 경로 변경을 유지한다.
- 장면별 속도는 목적을 유지하며 상대적인 어색함을 줄인다. 새 걷기를 과시하려고 긴 자동 이동을 강요하지 않는다.
- 전체 sprite를 늘였다 줄이거나 흔드는 것만으로 '걷기 완료'라고 하지 않는다. 일관된 프레임을 만들 수 없으면 필요한 아트와 이유를 명시한다.
- 현재 지원하는 외형 조합을 먼저 열거하고 성별·얼굴·안경·헤어·의상군의 대표 조합을 확인한다. 하드코딩된 첫 의상만 성공하는 구현을 피한다.
- 아틀라스는 필요한 단계에 준비하고 재사용한다. 모든 조합을 다시 boot에서 생성하지 않는다. 사진 결과/군중의 기존 pose와 크기가 회귀하지 않아야 한다.

### C-P01 박수

C 검수에서 박수는 주로 `짝짝!` 문구로 표현되고, 환호의 V 포즈보다 몸동작이 약하게 보였다.

- 손을 모았다 벌리는 작은 박수 동작 또는 인물의 손과 연결된 명확한 박수 표현을 만든다. 기존 외형에 맞춰야 한다.
- 인물/커플의 반응 문구는 주체 가까이 배치하거나 작은 말풍선 꼬리로 연결한다. 얼굴을 가리거나 두 문구가 겹치지 않게 한다.
- 기존 하트/`고마워 ♥`, 전체 구도, 약 1.25초의 짧은 정상 반응, 단체사진으로 한 번만 전환되는 구조를 보존한다.
- 커플 위치를 바꾸거나 전체 화면 컨페티/흔들림을 넣지 않는다.
- 감소 모드에서는 박수와 환호를 구별하는 정적인 포즈/표식을 사용한다.

### 완료 조건

- 무음 정상 영상만 봐도 걷기·멈춤·박수·환호가 구별된다.
- 머리/옷/발이 프레임마다 어긋나지 않고 도착 시 pivot 점프가 없다.
- 양측·키보드/포인터·감소 모드에서 예식 진행 1회, 입력 반복/청첩장 왕복에도 중복 전환 없음.
- 정상 연출 클립에는 청첩장을 중간에 열지 않는다. pause/resume 검증은 별도 clip/로그로 유지한다.

## 11. F24 — 실제 작업 전 대상 선별만

`F24_ART_TRIAGE.md`에 현재 화면을 보고 다음만 기록한다.

`장면/에셋 → 원본 크기 → 표시 크기/스케일 → 실제로 보이는 문제 → 권장 최소 변경 → 예상 영향/근거 캡처`

- 같은 픽셀 밀도가 아니라는 이유만으로 모든 에셋을 오류로 분류하지 않는다.
- 모바일에서 실제로 선/글자/얼굴이 무너지거나 원근이 어색한 후보를 0~5개 수준으로 선별한다. 반드시 문제를 채울 필요는 없다.
- 코드의 위치/크기 변경과 아트 재수출/수정이 필요한 문제를 구분한다.
- 실제 사진은 의도된 다른 레이어다. 픽셀화하지 않는다.
- 이번에는 전역 재수출·일괄 resize·추가 필터링 변경을 하지 않는다. F19/F23의 명시적 범위는 제외다.

## 12. 내부 작업 순서

1. baseline 보존, 현재 코드/목록 확인.
2. D-A01 정리와 음성 테스트 → 정상 shipping 검사. blocker가 있으면 숨기지 않는다.

7. 소스 고정 후 최종 production build, shipping assets, 전체 관련 회귀/production 테스트, 화면/동작 검증.

소단위별 로컬 검증은 하되 전체 회귀를 코드 한 줄마다 돌리지 않는다. 소스가 바뀐 뒤 예전 실행의 PASS를 최종 결과인 것처럼 합치지 않는다.

## 13. 최종 검증 기준

### 여정

- 신부측+자차와 신랑측+지하철 각각 정상 완주. 반대 조합의 경로/필수 조건도 대표 검사.
- 식사 먼저/나중, 박수/환호, 저장/메시지 생략, intro skip, 중간 청첩장/복귀, 재시작.
- 포인터 및 키보드-only. 완주 증빙에 강제 focus/진행 플래그 주입/시간 가속을 사용하지 않는다. 단위/고립된 장면 fixture는 분리해 표시한다.
- 두 사진 결과 5.5초 이상 유지, 수첩 재열람, 재방문/재촬영, reload/continue 시 사진 의미/진행도 일치.
- 잘못된 벽/가구 클릭, 에스컬레이터 우회, 접근점/돌아온 위치 유지.

### 화면·동작

- 320×568 / 393×852 / 430×932 / 852×393 / desktop 1440×900 DPR1. DPR3 대표 캡처.
- 이름/메시지 입력, 로비/HUD/패널/사진 결과에 잘림·겹침·44px 타깃 회귀 없음.
- 정상/감소 모드, 장면 중 청첩장 왕복/빠른 반복 입력, 긴 대기/복귀.
- 지원 브라우저 검증을 추가할 수 있으면 시도하되 설치된 실제 엔진/프로젝트를 적는다. WebKit 자동화는 실제 iPhone 검증과 구분한다. 미실행 플랫폼을 PASS로 적지 않는다.

### 성능/자원

- 동일 방법 production cold-cache 첫 화면 전체/게임 에셋, 각 경로 첫 로비 누적량. baseline 대비 증감을 기록한다.
- 실제 사용 중인 애니메이션/사진/군중 리소스가 반복 방문/재시작에 계속 늘어나지 않는다. lazy loading의 정당한 최초 증가와 누수를 구분한다.
- 저장값 크기와 저장 불가 처리, checkpoint/photo 재구성의 비용을 기록한다.
- 정상 여정의 page/console error, 실패 요청, missing texture를 기록한다. 의도적 실패 주입은 별도 집계한다. 에셋 검사 FAIL을 브라우저 PASS 뒤에 숨기지 않는다.

### 테스트 진실성

- 모든 테스트명/프로젝트/시도/상태, skip 사유와 다른 환경의 대응 실행을 보존한다.
- 재시도와 실패 후 별도 실행을 구분한다. 테스트 수정 이유와 사용자 관점 검증이 유지되는지 설명한다.
- 구현 자체의 dataset 값만으로 새 기능을 통과시키지 않는다. 실제 표시/입력/네트워크/저장/시간 변화와 교차 확인한다.
- 테스트를 고치기 위해 최소 크기·기존 필수 조건·재개 의미·검사 범위를 낮추지 않는다.

### 짧은 동작 영상

원래 속도/읽을 수 있는 해상도로 아래를 남긴다. 관련 구간 앞뒤만 잘라 정상 흐름을 보이고 실패를 편집으로 숨기지 않는다.

1. 중간 청첩장 진입 없는 정상 박수 → 단체사진.
2. 같은 조건의 정상 환호 → 단체사진.
3. 이동 → 방향 변경/장애물 우회 → 정지. 손/발/피벗이 보이게.
4. 사진/진행을 남긴 뒤 reload → continue → 수첩 확인.
5. 정상/감소 모드의 대표 촬영 비교.
6. 새 주차 안내와 뷔페 카드 상호작용(짧게 분리 가능).

pause/resume와 입력 반복은 정상 연출 클립과 구분된 테스트/별도 짧은 증빙으로 남긴다. 영상 생성 불가 시 시간 정보가 있는 프레임과 로그로 대체하고 한계를 명시한다.

### 크기와 보존

- 검수용 ZIP은 가능하면 **200MB 이하**. 원본 PNG/필수 UI 가독성/동작 타이밍을 희생하지 않는다.
- 성공 full-run 장시간 영상·대형 trace·중복 report는 로컬 원본에 보존하고 경로/해시/제외 이유만 남겨도 된다.
- 실패 개별 결과와 원인 진단 기록을 제거하지 않는다. 꼭 필요한 실패 trace가 크면 위치/핵심 오류 문맥을 포함하고 미포함을 명시한다.
- `node_modules`, 빌드 전체, 과거 배치 ZIP, `.DS_Store`, `__MACOSX`, 비밀정보, 폰트 바이너리를 검수 전달 파일에 넣지 않는다.
- ZIP 내부 파일 목록/CRC/해시를 확인한다. 원본 보존과 검수 ZIP 포함 범위를 구분한다.
